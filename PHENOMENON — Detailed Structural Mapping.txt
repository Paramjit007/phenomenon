 PHENOMENON_Compraventa_Terreno_Completo
  What the document adds vs. what's already built:

  The current COMPRAVENTA_SOLAR template handles the suspended condition mechanism well. This document adds three deeper philosophical layers:

  1. Traditio vs. escritura pública (Art. 1462 CC) — the document insists that the escritura is not real traditio. Our current implementation has no distinction between the two — a
  field for "Forma de entrega" but no engine logic validating whether real traditio has occurred separate from the escritura.
  2. Ser / Bien / Cosa distinction — the Registro diffuses the "bien" (property right), not the "ser" (ontological being) or the "cosa" (physical object). The engine doesn't currently   model this — it treats the Registro as a simple oponibilidad toggle.
  3. Condición urbanística ≠ prestación del contrato — the condition is a logical IF in the prosecución, not a guaranteed obligation. Currently we model it as a binary CONDICION_SOLAR   status, which collapses this distinction.

  What would need to be built:
  - New homologation checks distinguishing: traditio_real (has actual delivery happened?) from traditio_instrumental (escritura signed)
  - Engine logic for IF_logica vs. IF_temporal — currently all IFs are just cascade triggers, not typed
  - New field: condicionType: "prosecución lógica" | "prestación garantizada" to avoid confusing the seller's urban quota payments with a delivery guarantee
  - A "Resolución vía 1255 CC vs. 1124 CC" field that the risk engine uses to show the difference

  Feasibility: High — it's mostly adding depth to existing structure. 3-4 days of work.

  PHENOMENON_Caso_KPMG_Completo

  What the document reveals vs. what's already built:

  The current KPMG demo implements the financial layer (arrendamiento de cosa futura + circumcontrato CA2 + hipoteca + cesión). This document is about a completely different layer:
  corporate structural validation — the modular audit/compliance/governance structure.

  The document's A1 central is "Validación estructural corporativa" — not a financial transaction but a corporate approval workflow. It describes:
  - SA = internal agreements, preliminary validations, documentary conformities
  - CA = delivery of documents, review, approval, audit, signature, verification
  - IF = "if no compliance approval → next node cannot activate" — a logic gate

  This is fundamentally different from what we built. Our KPMG demo shows a bank financing a hotel. This document describes KPMG's internal validation/audit/compliance processes —
  using PHENOMENON to structure who approves what, in what order, with what conditions.

  What would need to be built:
  - New template type CORPORATE_VALIDATION or KPMG_CORPORATE
  - New contract types: COMPLIANCE_REPORT, AUDIT_APPROVAL, REGULATORY_SIGN_OFF
  - New IF type: IF_logic_gate — a blocking condition (node B cannot activate until node A is VALID)
  - A DAG (directed acyclic graph) visualization showing approval chains — different from the current radial graph
  - The "Pantalla 6: Informe estructural final" = what the engine currently calls the Ecosystem panel, but extended with compliance/audit specific fields

  Feasibility: Medium-high. The most valuable new feature is the logic gate IF — this is genuinely new to the engine. 1 week of work to do it properly.

  What's genuinely new vs. what the engine already has:

  Currently the engine has no concept of:
  1. Riesgo como fenómeno — risk is not just a label but a quantifiable vector with a probability, a severity, and an activation threshold. This needs a new RiskVector model in the
  engine.
  2. Exclusión como IF_oposición — exclusions are conditions that BLOCK activation. Currently IFs only cascade NEEDS_REVIEW; they don't BLOCK a phenomenon from activating.
  3. Sinestro como evento de transformación — a claim (siniestro) transforms the policy from "active coverage" to "claim processing" to "paid/rejected". This is a phase transition
  (F1→F2→F3) that needs the PhaseEngine to be wired into the frontend.
  4. Comparative view — showing 4 insurance types side-by-side is a new UI paradigm. The current graph is single-ecosystem; the document calls for a multi-ecosystem comparison view.

  What would need to be built:
  - 4 new templates: SEGURO_VIDA, SEGURO_RC, SEGURO_DANOS, SEGURO_CREDITO
  - Each generates sub-contracts: COBERTURA (the activated coverage), EXCLUSIONES (the blocking IFs), SINIESTRO (the claim event)
  - New IF_exclusion type in the engine that BLOCKS (not just flags) activation
  - New phase: ACTIVE_COVERAGE → SINIESTRO_PENDIENTE → INDEMNIZACION_PAGADA | RECHAZO
  - The "Pantalla 3: Mapa acetatial comparado" = a new 4-column comparative dashboard showing the 4 insurances side-by-side with shared structure highlighted

  Feasibility: High, but requires the most new engine work. 2 weeks for a proper demo.
