01 — What is this document, honestly?

"Insurance does not pay another party's debt. Insurance indemnifies an insured object (ferencia sensual) that has been actualised by a claim event." — PHENOMENON III governing formula

PHENOMENON_III_Flujograma is an operational clarification document, not a new theoretical layer. Its purpose is to fix how the insurance phenomenon is modelled. The current Seguros case in the application treats each insurance product as a master contract with three sub-contracts (COBERTURA, EXCLUSIONES, PRIMA). That structure is fine for demonstrating combinatorics, but it is architecturally wrong from a phenomenological standpoint. Insurance is not one phenomenon with accessories — it is three connected phenomena that open sequentially.

F1 — Coverage (always exists)

The insurance contract is live. The insurer is currently providing the service of coverage (IA co-activa). The premium pays for this present service, not for a future payment. The insured object (ferencia sensual) is covered but not yet damaged.

F2 — Claim (opens only when loss occurs)

A specific claim event (CST) actualises the insured object. F2 is NOT pre-existing — it is created when the loss happens. The indemnification is born here via ID 1089 (Art. 1089 CC). This is NOT paying a debt and NOT automatic subrogation.

F3 — Recovery (eventual, if culpable party)

Only opened after F2 if a liable third party exists. It is its own independent legal path (Art. 1902 CC), not an automatic reflection of F2. F3 does not always exist. Never confuse it with F2.

02 — Is it safe to implement? Will it break anything?

Short answer: YES, safe to implement — but in phases, not all at once

The document introduces new concepts that can be added on top of the existing architecture without deleting anything. The risk of breaking existing functionality is LOW if you follow the phased approach described in section 07. The current Seguros demo (16 phenomena, the comparative view, all cross-policy IF edges) continues working untouched while you build the new F1/F2/F3 layer in parallel.

HIGH RISK if done before new structure is fully tested. Do NOT do this in Phase 1.

Zero impact. Those cases are completely isolated from Seguros.

The one thing that can go wrong

The only real risk is trying to replace the current flat 16-phenomenon Seguros demo before the F1/F2/F3 structure is complete. The current demo works and impresses investors. Keep it working. Build F1/F2/F3 as a parallel demo route (setup-v2) and only cut over once it is fully tested and visually richer than what exists today.
