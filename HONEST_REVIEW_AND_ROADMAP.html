PHENOMENON — Honest Review, Diagnosis & Strategic Roadmap

A no-marketing assessment of the engine, the application, what is genuinely unique, what is missing, and how to move from "demo" to "product lawyers and registrars can actually use."
Document built: 2026-05-20 · Audience: project owner · Status: pre-build, alignment document

0. Executive Verdict (read this first)

What is genuinely strong: the cascade + ecosystem homologation. No mainstream contract product does network-level validation. That is the real product.
What is impressive but not yet defensible: the philosophical framework (ESS / AG / IA / IF / Opus). Lawyers will not buy ontology; they will buy "the system tells me when changing clause X breaks contract Y." Sell the cascade, keep the ontology as the internal model.
What is honestly missing: no authentication, no audit trail with user identity, no .docx export, no real Catastro/Registro integration, no error boundaries (one bug = blank page), no engine unit tests, no migration system. None of this is hard; none of it is built.

The one-paragraph honest pitch

PHENOMENON is a contract intelligence system where contracts are not isolated documents but a network. Change a date on the master, and every sub-contract updates and is re-validated automatically. Change an exclusion on a credit insurance, and the dependent coverage activates. We have 66/66 E2E tests passing, three working demo cases (KPMG €100M financing, multi-policy insurance, sale of land), and an interactive graph with live financial flows. We do not yet have: real lawyer-grade .docx export, authentication, integration with the Registro de la Propiedad, or unit tests on the engine itself. The cascade is the moat. Everything else needs four weeks of unglamorous work.

1. The PHENOMENON Engine — Complete Diagnosis

1.1 What it is (in plain language)

An ontological framework that models any entity as a phenomenon with five dimensions:

ConceptPlain meaningIn a contract
ESSStable identity — what makes the thing itself.Parties, jurisdiction, effective date, expiry date.
AGOperational content — what the thing does, the actions and obligations.Clauses, payment terms, deliverables, prices.
IAOperators — active/passive/prohibition/reciprocal vectors that classify obligations."Active obligation" (1088 CC), "Prohibition" (non operator), etc.
IFInter-phenomenic connections between entities.Master→sub, sub→sibling, exclusion blocking another coverage.
OpusDegree of effect/perfection.Eficacia entre partes → Plena → Oponible erga omnes (Art. 32 LH).

Crucially, the framework is domain-agnostic. We applied it to contracts, but the same engine could model corporate governance chains, supply-chain SLAs, or healthcare consent networks.

1.2 What it can do (theoretical capacity)

Any system where these five conditions hold can be modeled:

  1. Entities have stable identities that should not silently mutate.
  2. Entities have operational state that does change.
  3. Entities relate to other entities via typed links.
  4. A change to one should propagate to its neighbours, and the propagation rules are knowable.
  5. Validity of the whole is not just the sum of validity of the parts — coherence across the network matters.

1.3 What we have actually built (today)

Engine-level (Python, packages/engine/)

  • CASCADE_MAP — master ESS change → propagates to all sub-types
  • SUB_CASCADE_MAP — sub change → propagates to siblings (typed rules)
  • REVERSE_CASCADE_MAP — sub change → flags master for review
  • EcosystemEngine — 6 cross-contract consistency rules
  • Coverage checker — required sub-types per master template
  • Opus 3-level homologation
  • Phase lifecycle (ACTIVE → SINIESTRO_PENDIENTE → INDEMNIZACION_PAGADA / RECHAZO)
  • BLOCKED status via IF_exclusion (non operator) for insurance

API surface (FastAPI, backend/app/)

  • /phenomena CRUD + terminate
  • /cascade/trigger, /cascade/sub-trigger, /cascade/reverse-trigger
  • /ecosystem/{id}/homologate, /add-party, /add-contract
  • /demo/kpmg/seed, /demo/seguros/seed
  • /demo/seguros/siniestro, /demo/seguros/unblock-coverage
  • /demo/kpmg/update-euribor, /demo/amortization

1.5 What is genuinely missing from the engine

Functional gaps

  • Edge conditions not persisted (in-memory only)
  • No async cascade — large networks will block the request
  • No transactional cascade rollback if one step fails
  • No cascade history log (who triggered what when)
  • No custom rule definition (rules are hardcoded Python)
  • No rule versioning — changing a rule breaks history
  • No conflict resolution policy when two cascades target the same field
  • No prioritization or weighting of risks

Engineering gaps

  • No unit tests on the engine itself (only E2E through UI)
  • No property-based tests (cascade exhaustiveness)
  • No type hints / mypy enforcement on engine modules
  • No formal data model documentation (only code is canonical)
  • No engine API for non-FastAPI consumers
  • No SDK / client library
If unit tests existed on the engine, the "CASCADE_MAP missing KPMG types" bug would have been caught on the day FINANCIACION was added. We only caught it when an E2E test for the UI failed downstream. This is the single highest-leverage thing missing from the engine.

5.3 Self-healing test loop (proposed)

A script that on test failure:

  1. Captures the failing test name + screenshot + console errors.
  2. Categorizes the failure (network / locator / assertion / cascade / render).
  3. Looks up the category in a known-fix table (ERROR_DASHBOARD pattern table).
  4. Either auto-applies the fix (for known patterns) or files an entry in BUG_QUEUE.md.
  5. Re-runs only the failing test.
  6. Updates ERROR_DASHBOARD.md with current pass rate.

This is a half-day of bash + node scripting. It is the right answer to "how do I find bugs without me telling you."

5.4 Engine-logic tests that must exist (priority list)

  1. Every sub-type in _ALL_SUB_TYPES receives every ESS field cascade. (Catches CASCADE_MAP gaps.)
  2. Every SUB_CASCADE_MAP entry propagates without infinite loop.
  3. Every REVERSE_CASCADE_MAP entry sets master NEEDS_REVIEW.
  4. Every CONSISTENCY_RULE fires when violated; does not fire when satisfied.
  5. Every required-coverage rule flags missing types.
  6. Terminate cascades NEEDS_REVIEW to siblings and master.
  7. Add-party propagates to every contract in ecosystem.
  8. Homologation is idempotent (run twice = same result).
  9. Phase transitions only allow valid next states.
  10. BLOCKED status cannot become ACTIVE without explicit unblock.

6.2 Proposed performance dashboard (CLAUDE_PERFORMANCE.md, to build)

One markdown file tracked across sessions with:

  • Per-session score (0–100): tests run? docs updated? browser verified? proactive bugs found?
  • Bug ownership ledger: bugs-I-caught vs bugs-you-caught. Goal: > 70% me.
  • Time-to-fix: average minutes from bug-shown to bug-resolved.
  • Regression rate: how often a fix breaks something else.
  • "Done" reliability: how often "done" actually means done on first browser check.
  • Doc drift: SYSTEM_STATUS lag behind code.

It is updated at end of every session. You read it. If the metrics drift, you can call it out concretely.

6.3 Enforcement mechanisms (the actual control loop)

  1. Pre-task checklist (in CLAUDE.md): every task starts with "read these 3 files, run smoke tests, list affected modules."
  2. Pre-done checklist: "tests run? browser opened? SYSTEM_STATUS updated? CHANGES appended? screenshot saved?"
  3. Hooks: file-watch hook that runs npm run test:smoke on save, and writes the result to a known location I must consult.
  4. Activity log: a JSON file written at every "I am done" claim with the artifacts I produced. You can audit it.
  5. Bug ledger: BUG_QUEUE.md auto-populated with anything failed in last test run. Empty queue is the only "green" state.
